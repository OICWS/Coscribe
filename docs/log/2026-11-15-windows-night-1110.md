# Hand-fired scheduled runs in tests get 30 s, after the Windows night of 11-10 (shipped)

Why: the scheduled Windows run of the night of 11-10 (run 42928421698, main at 205ec6f) failed one
test, `test_approval_mode_auto_or_skip_auto_approves_a_gated_call[auto]`: the run came back
`completed` but `note.txt` was never written. It passed on every night since and 30 times in a row
on Linux.

## Shipped
- `tests/test_scheduled_tasks_resume.py`: the four hand-fired runs that still had a 5 s limit get
  30 s, as the three beside them did after the night of 11-09. The limit only stops a hang; nothing
  asserts on time.
- Cause, reproduced on Linux: when `asyncio.wait_for` cancels a run while its turn is in a model
  call or a tool call, the turn swallows the cancellation and `fire_trigger_now` returns the run as
  `completed`, with no file written. A slow runner that passes 5 s inside the turn gives exactly the
  failure seen on Windows; the cancellation earlier, while the run is still being set up, raises
  `TimeoutError` instead.
- `docs/plan.md`: the maintainer's decision that the night of 11-10, like 11-09, does not restart
  the count; the count is 16 of 14, so the job can be made required.

## Not verified
- Only Linux locally; the next scheduled Windows nights are the check.

## Follow-ups
- A run whose turn is cancelled from outside is recorded as `completed` (in `docs/plan.md`); whether
  a server shutdown during a run does the same is not checked.
