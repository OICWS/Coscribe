# Nightly Playwright run against the stub model (shipped)

Why: issue #116. The 17 Playwright specs ran only by hand, so a UI regression showed up when someone happened to use that screen.

## Shipped
- `.github/workflows/e2e.yml`: nightly and `workflow_dispatch` (and a pull request that changes this file only), Linux, report only. It builds the frontend, installs Chromium, starts `scripts/stub_llm.py`, `coscribe-web` (from a scratch directory with its own `.env`, workspace and state) and `vite`, runs the specs listed in the workflow's `SPECS` variable, writes a job summary, and uploads the Playwright report and traces on failure.
- `SPECS` is the one list. Left out: `approval.spec.ts` (needs a model that calls a tool) and `chat.spec.ts` (checks the answer "4"; the stub says "OK").
- `secrets.spec.ts` needs a keychain; the job gives the server `keyrings.alt`'s file backend through `PYTHON_KEYRING_BACKEND`. `labels.spec.ts` imports a source file, so the specs run against `vite`, not the built bundle.
- No spec and no app code changed.

## Not verified
- A scheduled (nightly) run: it happens after merge. The same job ran green on the pull request (28 tests).
- Windows and macOS (the job is Linux only, by design).
- `skill-plugins.spec.ts` installs a plugin and leaves it: a second run against the same workspace fails (the button says "Added", not "Add"). The CI workspace is fresh each run, so this does not matter there; it matters for anyone who reruns the spec locally.

## Follow-ups
- `approval` and `chat` need a model that calls tools and does arithmetic; they stay out until a scripted stub can answer them. `docs/plan.md` is updated once at the end of batch 2 (#105), not here.
